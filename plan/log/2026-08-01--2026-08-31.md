# 8月技术报告

## 目标与问题

8 月的主线是推进 x86_64 Guest UEFI 支持：在已有 OVMF、fw_cfg 和 ACPI 启动链路的基础上，先建立可复现、可归因的验证基线，再补齐标准 PCI 设备模型，为后续 virtio-blk PCI 启动盘和 OVMF 启动路径铺路。

本月重点解决以下问题：

1. OVMF 启动验证缺少固件来源、VMX/SVM 对称覆盖和 ACPI table-loader 逐项断言，难以判断 guest 是否真正完成了固件到 Linux 的交接。
2. 共享 virtqueue 面向不可信 guest 时缺少完整的环布局校验和运行期故障隔离，异常 guest 数据可能导致错误被吞掉或继续访问 guest 内存。
3. x86 vCPU 的 NPF/EPT 解码器此前只识别 LAPIC、IOAPIC 且只支持 dword 访问，无法承载普通 PCI BAR 的 byte/word 等宽度访问。
4. x86 PCI 路径只有硬编码的 host bridge 和 LPC bridge，普通设备模型无法在统一设备图中声明 PCI function、BDF、BAR 和 runtime route。

## 计划安排

### 第一阶段：x86_64 Guest UEFI 诊断与持续验证

- [x] 固定并记录 OVMF 实际 CODE/VARS 及最终 guest 镜像的路径、大小和 SHA-256。
- [x] 增加 VMX/SVM 对称的 OVMF/ACPI 用例，并逐项验证 ACPI table-loader 的 allocate、pointer 和 checksum 命令。（#1931）
- [x] 将 SVM 版本接入 self-hosted AMD CI，形成持续回归覆盖。（#1959）

### 第二阶段：共享 virtqueue 安全加固

- [x] 修复 descriptor chain 的边界不一致问题。
- [x] 校验 descriptor、avail、used 三个环的对齐、溢出和互不重叠关系。
- [x] 将非法 guest 访问转换为 queue fault，停止后续读写并要求 reset 恢复。（#1984）

### 第三阶段：x86 通用设备访问与 PCI 基础

- [x] 让 x86 vCPU 根据 resolved device graph 接收普通设备 MMIO 区间。
- [x] 支持普通设备 MMIO 的 byte、word、dword、qword MOV 访问，并保持 LAPIC/IOAPIC 特殊路径不变。（#2082）
- [x] 建立统一的 typed vPCI core、BDF/BAR 规划、root config 路径和 x86 PCI 枚举验证。（#2197）

### 第四阶段：virtio-blk PCI 与 Guest 启动盘

- [ ] 在通用 vPCI foundation 上完成 modern virtio-blk PCI 设备和 ramdisk 后端的端到端验证。
- [ ] 验证 Linux guest 对 PCI block device 的枚举、读写和 flush 路径。
- [ ] 复用同一设备接入 OVMF，让 Guest UEFI 通过 VirtioBlkDxe 发现并尝试从 PCI 磁盘启动。

## 实现情况

### 已合入 PR

#### #1827 — `chore(repo): reference AGENTS.md with @ syntax in CLAUDE.md`（8-3 合入）

解决 Claude Code 不可以稳定加载仓库规范和相关 skill 条件的问题。

#### #1931 — `test(axvisor): validate x86 OVMF ACPI on VMX and SVM`（8-9 合入）

**要解决的问题**：dev 已具备 x86_64 Guest 的 OVMF、fw_cfg 和 ACPI 启动路径，但原有验证无法充分说明实际使用的固件资产、SVM 后端是否能复现相同链路，以及 table-loader 是否生成了完整正确的 ACPI 操作序列。

**主要改动**：

- 在准备 guest OVMF 镜像时记录实际 CODE、VARS 和最终镜像的路径、大小及 SHA-256，并区分 split CODE/VARS 与 monolithic CODE 布局。
- 新增与 VMX 共用 guest 配置、内核、initramfs、固件和成功断言的 `ovmf-acpi-svm` 用例，确保 VMX/SVM 的差异只来自外层 CPU 能力。
- 对 ACPI table-loader 的 allocate、pointer、checksum 命令逐项解码和断言，覆盖文件、偏移、范围、宽度及顺序。
- 更新 Axvisor 测试文档和 x86 UEFI 调试说明，明确证据来源和成功条件。

**验证结果**：`smoke-vmx`、`smoke-svm`、`ovmf-acpi-vmx` 和 `ovmf-acpi-svm` 均通过；OVMF 用例能够启动 Linux initramfs 并命中 `AXVISOR_X86_OVMF_ACPI_PASSED`。这建立了后续 PCI 和 virtio 设备开发所需的 UEFI 回归基线。

#### #1959 — `ci(axvisor): run ovmf-acpi-svm on self-hosted AMD CI`（8-11 合入）

#1931 已增加 `ovmf-acpi-svm`，但 CI 只运行 VMX 版本，SVM 后端缺少嵌套 OVMF/ACPI 路径的持续回归覆盖。本 PR 在确定本机 `ovmf-acpi-svm` 能够稳定后，接入 CI。

#### #1984 — `fix(axvirtio-common): harden shared virtqueue against untrusted guests`（8-13 合入）

**要解决的问题**：共享的 `axvirtio-common::VirtioQueue` 被 `axvirtio-net` 和 `axvirtio-blk` 共用，但面向不可信 guest 时存在以下缺口：descriptor chain 的边界判断不一致；三类 ring 缺少对齐、溢出和重叠校验；`QUEUE_READY` 可以在未验证布局上生效；错误类型无法区分非法布局和需要 reset 的运行期故障。

**主要改动**：

- 统一 descriptor chain 长度边界，修复合法全索引链被拒绝的问题。
- 新增 `validate_layout()` 和带 guest memory 的布局校验，检查三环地址、对齐、范围溢出、互不重叠以及 EVENT_IDX footer。
- 增加 `faulted` 状态：运行期 ring 或 descriptor 校验失败后停止 `pop`、`complete` 和 guest-data 访问，避免继续写入 guest 内存；`reset()` 清除故障状态。
- 将 `QUEUE_READY` 收敛为经过 scoped guest memory 校验的单一生效点，并补充 `RingMisaligned`、`RingOverlap`、`InvalidRingLayout` 和 `QueueFaulted` 错误。
- 同步接入 `axvirtio-net` 和 `axvirtio-blk`，避免故障被当作空队列吞掉，也修复 scoped-memory ready 校验遗漏。

**效果**：所有现有及后续 virtio 设备共用同一套 ring 布局校验和 fault 语义，为 virtio-blk PCI 复用共享队列提供了安全基础。

#### #2082 — `fix(x86_vcpu): decode generic device MMIO of arbitrary width on NPF/EPT`（8-19 合入）

**要解决的问题**：#2070 的 virtio-blk-pci 设备已经可以被 Linux 枚举、分配 BAR0 并绑定 virtio-pci 驱动，但 guest 对 BAR0 的 byte 写会触发 NPF/EPT。旧解码器无法识别普通设备 MMIO，RIP 不前进后 guest 进入无限循环。

**主要改动**：

- 将 VMX EPT 和 SVM NPF 的 MMIO 判定从 LAPIC/IOAPIC 特判扩展为 resolved device MMIO 区间。
- 新增 `X86InterceptedMmioRange`，由 `axvm` 从 resolved device graph 收集并随 vCPU setup 下发。
- 对普通设备路径按 opcode、`0x66` 操作数尺寸前缀和 REX.W 解码 byte、word、dword、qword 的 MOV 访问，并将真实访问宽度传递到既有 `DeviceRuntime` 分发链。
- 保留 LAPIC、IOAPIC 的既有特判和 dword 语义；未命中设备 MMIO 的 NPF 仍返回明确的 `NestedPageFault`。

**验证结果**：补充 MMIO 宽度、区间边界、非法配置和 resolved graph 下发测试；联合 #2070 验证时，原有 `stage2 query miss / unhandled x86 nested page fault` 死循环消失，guest 能继续进入 virtio-blk probe 阶段。

#### #2197 — `feat(axvisor): add generic vPCI foundation with x86 PCI enumeration`（8-28 合入）

**要解决的问题**：现有 x86 PCI 配置模型只有硬编码的 Q35 host bridge 和 LPC bridge，普通 `DeviceModel` 无法声明 PCI function，BDF、BAR placement、firmware 资源和 runtime route 也没有统一的设备图所有权，后续每增加一种 PCI 设备都需要修改架构私有代码。

**主要改动**：

- 在 `axdevice` 增加 typed PCI 基础类型和描述符，包括 `PciSegment`、`PciBdf`、`PciBarIndex`、`ConfigOffset`、`PciMemoryBar` 和 `PciEndpointIdentity`，在构造阶段完成边界校验。
- 将 BDF、BAR 按确定性规则解析并冻结到现有 `ResolvedDeviceGraph`，统一处理 host、endpoint、依赖关系、资源冲突和失败回滚。
- 新增通用 `PciRootState`、PCI function runtime binding、BAR probe/relocation 和 endpoint route token。
- 将 x86 前端收敛为 CF8/CFC 配置访问机制，Q35/LPC 与普通 endpoint 共享同一 root lookup；ACPI `PCI0/_CRS` 的 memory window 从 resolved aperture 推导。
- 增加 test-only PCI endpoint 和 VMX/SVM 对称的 Linux `lspci` 验证，检查 function identity、BAR 分配和资源属性。

**验证结果**：Linux guest 已能通过 `lspci` 枚举测试 PCI function，并识别已分配的 BAR memory resource。vPCI foundation 与 x86 枚举路径已经合入，后续 virtio-blk PCI 可以在统一 PCI 设备边界上继续实现。

### 未合入与持续推进

#### virtio-blk PCI 数据盘

8 月中旬开始的 virtio-blk PCI 工作经历了一轮边界重构：先以只读 modern virtio-blk PCI 数据盘为目标，随后根据评审意见复用通用 vPCI、共享 block core 和 virtqueue，避免为 PCI transport 再复制一套 block 实现。

当前本地实现已经能够在通用 vPCI 上接入 modern VirtIO Block，并补齐 PCI capability、BEM/DMA 和 INTx 路径；ramdisk 后端支持同步 read、write、flush 语义。该部分尚未作为本月合入 PR 交付，端到端验证仍受 Linux guest 启动阶段两个长时间卡点影响：

- `APIC: Switch to symmetric I/O mode setup` 阶段可能停留 6—7 分钟；
- FPU xstate 初始化阶段可能停留 3—4 分钟。

因此目前可以确认 PCI foundation 和普通 BAR MMIO 已经打通，但尚不能将 virtio-blk PCI 的完整设备 probe、磁盘读写、flush、guest marker 或 OVMF 启动盘能力写成已完成。后续需要先定位并优化上述启动卡点，再完成 Linux guest 的完整证据链。
