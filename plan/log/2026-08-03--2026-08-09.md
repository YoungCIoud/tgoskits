## 1. PR #1931 — x86 OVMF ACPI 验证合入

### 完成内容

最新 dev 已具备 x86_64 Axvisor guest 的 OVMF、fw_cfg 和 ACPI 启动路径，并已有 VMX `ovmf-acpi` 用例能启动 Linux initramfs，但现有证据不足以稳定回答：本次运行实际使用了哪份 Ostool OVMF、SVM 是否能以相同 guest 配置到达同一成功条件、fw_cfg ACPI table-loader 是否生成了完整且顺序正确的 allocate/pointer/checksum 命令、`AXVISOR_X86_OVMF_ACPI_PASSED` 究竟证明了哪段启动链路。

本 PR 只补齐当前实现的验证与说明，不新增 guest UEFI 产品 feature：

- 准备 x86 guest OVMF 镜像时记录实际 Ostool CODE、VARS 和最终 guest image 的路径、字节数及 SHA-256；区分 split CODE/VARS 与 monolithic CODE 布局，验证最终镜像固定为 4 MiB；
- 新增 `ovmf-acpi-svm` 用例，与 VMX 用例共用同一个 build config、guest TOML、BusyBox initramfs、OVMF 镜像和成功断言，两者只在外层 QEMU 暴露的 VMX/SVM CPU 能力上不同（Axvisor 仍按运行时 CPUID 选择 backend），保证结果差异可归因于 backend 而不是不同 guest 配置或固件资产；
- 扩充 ACPI table-loader 最低层测试，逐项解码并验证 table/rsdp 分配、FADT/XSDT/RSDP 指针修正以及各 ACPI 表 checksum 命令的文件、偏移、范围、宽度和顺序；
- 更新 Axvisor 测试文档和 x86 UEFI 调试说明，明确运行命令、证据来源、成功条件以及当前不能据此声明的能力。

### 测试与验证

四个用例（smoke-vmx、smoke-svm、ovmf-acpi-vmx、ovmf-acpi-svm）全部通过，两个 OVMF 用例均命中 `AXVISOR_X86_OVMF_ACPI_PASSED`；`cargo fmt`、axbuild/axvm 针对性测试与 clippy 通过；mai-team-app 两轮 APPROVED（审查环境无 `/dev/kvm`，QEMU 端到端未重跑，与文档中按 Intel/VMX 或 AMD/SVM 宿主分别运行的前置条件一致）。

## 3. F2 阶段：PCI 只读数据盘（设计进行中）

在验证当前实现（阶段 V）并确认固件平台缺口（F1）无需修复后，F2 定位为第一个可用 feature 阶段：为 x86 guest 增加标准、只读的 modern virtio-blk PCI 数据盘。沿用当前 fw_cfg direct-boot Linux 路径，让 Linux 枚举该设备、挂载磁盘并读取固定 identity 文件；F3 复用同一产品设备推进到 OVMF 启动盘。

### 最小垂直链路

```text
guest TOML 只读磁盘后端
  -> Axvisor 在 VM build 前读取并冻结镜像
  -> resolved graph 中组合唯一 function 的 PCI root bus
  -> 4 KiB BAR aperture 和 resolved INTx route
  -> modern virtio-blk PCI transport
  -> direct-boot Linux virtio-pci / virtio-blk
  -> raw ext4 /dev/vda -> /axvisor/F2-ID.txt
  -> AXVISOR_X86_PCI_BLOCK_PASSED identity=axvisor-f2-readonly-data-v1
```

成功 marker 必须由 guest Linux 在核对实际 PCI identity、块设备只读属性和 identity 文件内容后写入 guest console；仅看到 PCI vendor/device、BAR 访问、virtqueue notify 或设备节点均不能完成 F2。

### 关键决策

- 采用 modern non-transitional virtio-blk（vendor `0x1af4`、device `0x1042`）；拒绝 legacy/transitional、fw_cfg 私有块设备、AHCI/NVMe/宿主直通；可写或宿主文件实时后端推迟到独立设计；
- 固定 BDF `00:03.0`、4 KiB 32-bit non-prefetchable BAR0、唯一 level-triggered INTx；PCI root-bus graph node 同时拥有 config PIO、BAR MMIO aperture、IRQ claim、guest-memory 声明和只读 block backend，endpoint 不再成为第二个 graph/runtime node；aperture base 与 GSI 由资源规划分配并检查冲突，不硬编码；ACPI `_CRS`/`_PRT` 与 runtime 使用同一 x86 machine/resolved plan，不允许 AML、config space 和 runtime 各自硬编码副本；
- VirtIO 1.2 协议面：queue 0、size 128 的 split virtqueue，只发布 `VIRTIO_F_VERSION_1` 和 `VIRTIO_BLK_F_RO`；不实现 MSI-X、packed ring、ring reset、indirect descriptor、event index、`VIRTIO_PCI_CAP_PCI_CFG`；只接受 `VIRTIO_BLK_T_IN`，写请求返回 `VIRTIO_BLK_S_IOERR`，未知请求返回 `UNSUPP`；初版同步处理 notify，reset 完成时不存在后台请求；
- 配置契约：`model = "virtio-blk-pci"`、`backend = { type = "file", path = ..., read_only = true }`，BDF/BAR/IRQ 等数值字段必须被拒绝，重复 model 在规划期报错；镜像经窄 image-provider 冻结为 `Arc<[u8]>` 不可变快照，原文件在 VM 运行期间变化不改变 guest 看到的内容；非 x86 架构按 unsupported 拒绝；
- 证据资产：8 MiB raw ext4（无分区表），固定 UUID 与 mke2fs 参数两次生成 SHA-256 相同；initramfs 完成 sysfs 只读核验（`/sys/block/vda/ro` 为 1、写 dd 确定失败）、`mount -o ro` 读取 identity、INTx completion 增长等检查后才输出 marker；VMX/SVM 使用同一 guest 配置与同一镜像 digest。

### 实施单元顺序

1. PCI root-bus 重构（行为保持，可作独立前置 PR）；
2. virtio-blk PCI 产品实现：split virtqueue/block core、modern PCI function、INTx、x86 planner、resolved resources、ACPI、配置解析与 immutable image provider 同一提交，保证新公共能力有真实调用方；
3. Linux E2E 与证据：外层 QEMU 经 ostool UEFI 流程启动 PE/COFF hypervisor，内层 `enable_bios = false` + `boot_protocol = direct`，不依赖嵌套 OVMF；
4. 验证记录：数据盘 digest、VMX/SVM backend 结果与已知限制。

### 当前状态

F2 设计已定稿（协议面、资源所有权、配置契约、证据步骤与退出条件完整），尚未开始产品代码实现。

## 4. 本周形成的关键结论

- `AXVISOR_X86_OVMF_ACPI_PASSED` 作为嵌套 Linux initramfs 判据，比"OVMF 首次访问 fw_cfg"更强：它只在 OVMF 完成 kernel handoff、Linux 进入早期用户态并完成 DSDT/APIC/FACP/SPCR/IOAPIC 等初始化后输出，不需要在产品代码中增加新的诊断 marker；
- 固件来源保持单一：OVMF 的版本选择、下载、缓存和完整性校验由 Ostool 负责，测试层只组装当前 guest 所需的 4 MiB 镜像并打印实际输入/输出摘要；
- VMX/SVM 对称验证只改变外层 QEMU CPU capability，保证结果差异可归因于 backend 而不是不同 guest 配置或固件资产；
- 协议错误尽量在最低层暴露：端到端用例证明完整启动结果，table-loader 单元测试直接检查固件将要消费的二进制命令布局，便于区分 loader 生成错误与固件/backend/guest OS 运行错误；
- 验证缺口（vPIC wire mode、PCI 中断、SMP）不会通过屏蔽 warning、放宽成功条件或扩大 timeout 处理，进入后续 feature 阶段。

## 6. 口述稿

本周主线是 x86_64 Guest UEFI 支持。

第一件事，验证 PR #1931 合入了 dev。之前 dev 上已经有 OVMF/fw_cfg/ACPI 的启动路径，但证据不够硬：到底跑的是哪份固件说不清，SVM 是不是也能用同一套配置跑起来也不知道，ACPI table-loader 生成的命令对不对也没有逐项验证。这个 PR 补齐了三块：一是装载时把固件路径、字节数、SHA-256 全部记录下来，二是加了和 VMX 完全对称的 SVM 用例，三是把 table-loader 的 allocate、pointer、checksum 命令逐条断言。现在 VMX 和 SVM 四个用例都通过了。

第二件事，F2 的设计基本定稿，还没开始写产品代码。F2 要做的是一块只读的 virtio-blk PCI 数据盘，让 guest Linux 能枚举到标准 PCI 设备、挂到 /dev/vda、mount 一个 ext4 镜像读到固定内容。关键决策都定了：固定 BDF 00:03.0 和 4KiB BAR，root bus 一个人持有 config、MMIO、INTx 和只读后端的所有权；virtio 只做 1.2 的 split virtqueue，只发布版本和只读两个 feature；配置层只让用户描述意图，不允许填 BDF、BAR、IRQ 这些数值；镜像在构建时冻结成不可变快照。证据口径也定了：guest 必须真的把盘挂上、确认只读、读到 identity 文件，才输出成功 marker，光枚举到设备不算。

下周的重点就是按实施单元顺序开工：先做行为保持的 PCI root-bus 重构作为独立 PR，然后一次性提交 virtio-blk 的产品实现，最后补 Linux 的端到端证据。
