# 9月技术报告

## 1. 目标与问题

9 月继续推进 [Discussion #1604 实习开发计划](https://github.com/rcore-os/tgoskits/discussions/1604) 中的 x86_64 Guest UEFI 支持。8 月已经合入 OVMF/ACPI 验证基线、共享 virtqueue 加固、x86 通用设备 MMIO 解码和通用 vPCI foundation。本月的任务是在这些基础上完成 virtio-blk PCI 数据路径，再让 OVMF 从 PCI 磁盘读取 ESP，经 GRUB 启动 Linux。

进入 9 月时，virtio-blk PCI 已有本地实现，但 Linux guest 的完整读写验证仍受启动阶段长时间停顿影响。后续尝试 UEFI 磁盘启动时，又暴露了块请求 feature 协商、Q35 ECAM 和 legacy PIC 中断投递的问题。这些问题分别位于设备协议、PCI 平台和 vCPU 中断路径，需要拆开修复，再同步回启动验证分支。

本月还需要明确启动盘的后端边界。同步 ramdisk 可以证明 PCI 块设备的读写链路，但完整启动验证需要提供包含分区表、ESP、GRUB、内核和 initramfs 的整盘镜像。原有 file 后端按 ext4 镜像检查文件，不能直接接受 GPT 启动盘，因此月底将验证方案调整为 raw 文件启动盘与 ext4 数据盘的双盘配置。

## 2. 计划安排

本月按“Linux 数据盘可用，再验证 UEFI 从盘启动”的顺序推进。

### 2.1 #2070 PCI 块设备数据路径

这一阶段复用 `ResolvedDeviceGraph`、共享 block core 和 virtqueue，完成 modern VirtIO PCI transport、DMA、INTx 与同步 ramdisk 的整合，并通过 guest 内部检查判断设备是否可用。

- [x] 完成同步 VirtIO block PCI ramdisk，支持 read、write、flush，并保留只读约束。
- [x] 补齐 feature 协商、queue address 分段访问、reset 和 PCI 生命周期处理。
- [x] 完成 Linux guest 块设备读写验证，合入 VMX/SVM 的只读、读写用例。

### 2.2 UEFI 启动依赖修复

排查启动问题后，将可以独立复用的修复拆成 PR，避免整条启动链路的审查同时承担设备协议和平台修复：

- [x] #2510：按协商结果应用 `VIRTIO_BLK_F_SIZE_MAX` 和 `VIRTIO_BLK_F_SEG_MAX` 请求限制。
- [x] #2501：补齐 Q35 ECAM、扩展配置空间分派和 ACPI MCFG 描述。
- [x] #2518：区分 legacy PIC 与 APIC 中断来源，修复 PIC 中断投递被 PPR 检查阻挡的问题。

### 2.3 #2275 UEFI 磁盘启动验证

这一阶段由 OVMF 从 VirtIO PCI 启动盘读取 GRUB，再加载 Linux 和 initramfs。成功条件由内层 guest 输出，检查启动来源与实际磁盘访问。

- [x] 提交 `boot_source = "pci-disk"`、raw file 后端和双盘测试配置。
- [x] 本地 SVM 双盘用例通过，验证启动盘和 ext4 数据盘的**写入及重挂载回读**。
- [ ] 补齐 VMX 双盘用例的运行证据，并建立 VMX/SVM 持续 CI 覆盖。
- [ ] 整理启动镜像发布方式，完成 #2275 合入。

目前的所用的启动镜像是在 CI 流程中注入 AxVisor FS 中的，路径为 `/guest/boot.img`。后续标准的做法应该是 tgosimages 发布的 `rootfs-x86_64-alpine.img` 已经直接放入了 boot.img 资产，AxVisor 能够直接使用而不需要目前“注入”的流程。

## 3. 实现情况

9 月共合入 4 个 PR，对应 4 个 squash 后的主线 commit。UEFI 磁盘启动方案仍在 #2275 中推进，月底版本包含 5 个提交。

### 3.1 同步 PCI 块设备

[PR #2070](https://github.com/rcore-os/tgoskits/pull/2070) 于 9 月 11 日合入，主线 commit 为 `f1fa3d4ee`。它解决了通用 vPCI 已能枚举设备、但 virtio-blk PCI 尚缺少完整数据路径的问题，将 modern VirtIO PCI 接入共享块请求处理逻辑和 ramdisk 后端。

主要改动包括：

- 复用共享 block core 和 `VirtioQueue`，由 PCI transport 提供 common config、notify、device config 和 ISR 访问。
- 将 PCI capability、BAR、endpoint DMA grant 和 INTA 路由接入统一设备图，固件描述与 runtime 使用同一份 `ResolvedDeviceGraph`。
- 补齐 queue address 的分段访问、VirtIO status 协商和 reset 处理；在 PCI 生命周期切换时协调在途访问、DMA 与中断发布，避免旧 callback 使用失效资源。
- 增加 Linux guest 的只读、读写用例，检查设备发现、实际数据访问和只读限制。

月初排查发现，本地 WSL 嵌套虚拟化环境运行很慢，是之前端到端测试超时的重要因素。随后转向远端 CI 验证，块设备读写测试通过，#2070 完成合入。这里交付的是同步 ramdisk 的 read、write、flush 能力；文件启动盘在后续 #2275 中继续处理。

### 3.2 块请求协商限制

[PR #2510](https://github.com/rcore-os/tgoskits/pull/2510) 于 9 月 25 日合入，主线 commit 为 `d31dd803a`。UEFI 磁盘读取过程中发现，设备此前直接按配置中的 `size_max` 和 `seg_max` 检查请求，即使 guest 没有协商对应 feature，也会套用这些限制。

本次将协商后的 feature mask 传入共享请求处理逻辑。只有协商 `VIRTIO_BLK_F_SIZE_MAX` 时才限制单段长度，只有协商 `VIRTIO_BLK_F_SEG_MAX` 时才限制数据段数量；MMIO 和 PCI transport 使用同一规则。同时处理 reset 后的协商状态，避免上一轮状态影响重新初始化。

这项修复使 OVMF、GRUB 和 Linux 按各自实际协商的能力访问磁盘，解除启动盘读取中的协议限制问题。

### 3.3 Q35 ECAM

[PR #2501](https://github.com/rcore-os/tgoskits/pull/2501) 于 9 月 26 日合入，主线 commit 为 `4e2e62f47`。之前 Q35 PCI root 主要通过 CF8/CFC 提供传统配置访问，缺少标准 ECAM 入口，guest 无法通过该路径访问 PCIe 扩展配置空间。

本次在现有 PCI root 上加入固定 ECAM 窗口，让 ECAM 与 CF8/CFC 共用 PCI function 分派，并修正扩展 offset 的访问处理。ACPI MCFG 发布窗口位置，根级 `PNP0C02` 声明保留区域，direct-boot Linux 内存图也标记这段窗口；这些信息来自同一份资源规划。

guest 用例增加 MCFG、`/proc/iomem` 和配置空间 offset `0x100` 检查，用来确认窗口描述和实际访问路径一致。该 PR 补齐了 UEFI PCI 平台入口，整盘启动结果仍由 #2275 的端到端用例验证。

### 3.4 Legacy PIC 中断投递

[PR #2518](https://github.com/rcore-os/tgoskits/pull/2518) 于 9 月 28 日合入，主线 commit 为 `7c79828fe`。排查 UEFI 启动中断路径时发现，legacy PIC 事件与固定 APIC 中断共用投递处理，PIC 事件可能被 vLAPIC 的 PPR 优先级检查挡住。

本次在排队和待投递事件中保留中断来源，通过 `QueuedVcpuInterrupt::LegacyPic` 和 `PendingEvent` 将 PIC 事件传到 VMX/SVM 注入路径。PIC 中断仍受 guest 的可屏蔽中断状态约束，但不再套用 LAPIC 的优先级筛选；APIC 中断继续遵循自身的优先级规则。

修复同时补充排队、来源传递和优先级行为测试。

### 3.5 UEFI 文件双盘启动

[PR #2275](https://github.com/rcore-os/tgoskits/pull/2275) 尚未合入。目前的思路是文件双盘方案：一块 raw 格式的 GPT＋ESP 盘负责启动，另一块沿用 Alpine ext4 镜像作为数据盘，不管是启动盘镜像还是数据盘镜像，都是AxVisor通过自己的FS找到的。

由 5 个提交组成，分别实现 raw file-backed block image（`8d1248ebc`）、PCI 磁盘启动配置（`a4383054c`）、OVMF TPM 探测兼容（`f0d437670`）、双盘用例（`33c1c90b7`）及文档（`06e639c87`）。其中 `image_format = "raw"` 允许 file 后端直接提供整盘字节内容；`boot_source = "pci-disk"` 让 OVMF 从盘中读取 GRUB、内核和 initramfs，这个字段将标准UEFI启动与当前直接通过 `fw_cfg` 注入的启动方式区别开来。

启动时还发现 OVMF 会探测 `0xfed4_0000` 的 TPM TIS 地址。当前实现为该窗口注册表示“没有 TPM”的兼容设备，读取返回对应宽度的全 1，写入忽略，使固件继续启动。这是针对已观察到地址的兼容处理，未分配 MMIO 的通用处理仍需后续整理。

双盘用例由内层 `/init` 检查启动盘专用内核参数、GPT 磁盘头、ESP 分区和另一块盘的 ext4 超级块。它分别读写挂载两块盘，写入标记，并在卸载、重挂载后回读；全部通过才输出 `AXVISOR_X86_UEFI_FILE_DUAL_DISK_PASSED`。本地 SVM 端到端用例已通过，VMX 仍需补齐运行证据。

测试资产目前保存在用例目录。`prepare_boot_image()` 校验并解压 `boot.img.gz`，`prepare_configured_boot_rootfs()` 将启动盘注入外层 Axvisor rootfs 的临时副本。副本在测试结束后清理，因此回读结果证明同一次运行中的磁盘读写和文件系统重挂载，不证明跨次运行持久化。最终启动盘尚未纳入 tgosimages 的发布资产。

远端 CI 规划器跳过了 fork PR 中需要自托管 KVM runner 的检查，因此 #2275 的远端绿色结果不包含 `uefi-file-vmx` 和 `uefi-file-svm`。本月已有本地 SVM 启动证据，完整的双平台持续验证仍未完成。

## 4. 整体进度

截至 9 月底，Linux PCI 数据盘与三项启动依赖修复已经进入主线。UEFI 文件双盘方案已有本地 SVM 通过记录，但代码合入、VMX 验证和发布镜像整合仍待完成。

| 模块 | 状态 | 说明 |
| --- | --- | --- |
| VirtIO block PCI 同步 ramdisk | 已合入 | #2070，完成 PCI 数据路径与 Linux guest 读写验证 |
| 块请求 feature 协商限制 | 已合入 | #2510，MMIO/PCI 按协商结果应用请求限制 |
| Q35 ECAM | 已合入 | #2501，统一配置分派、MCFG 与窗口保留描述 |
| Legacy PIC 投递 | 已合入 | #2518，保留事件来源并修正优先级筛选 |
| Raw 文件启动盘与双盘用例 | PR 待合入 | #2275，提供 GPT＋ESP 启动盘和 ext4 数据盘 |
| UEFI 双盘 SVM 端到端 | 本地已通过 | 检查 OVMF 到 Linux 的启动及双盘重挂载回读 |
| UEFI 双盘 VMX 与持续 CI | 待验证、待接入 | fork 的远端绿色状态未覆盖自托管 KVM 用例 |
| 启动镜像发布整合 | 待处理 | 目前通过临时 rootfs 副本注入启动盘 |

相较于月初，PCI 块设备已经完成合入，UEFI 磁盘启动也从启动阶段超时推进到本地 SVM 双盘用例通过。作为最后一个月的报告，最终交付范围是 4 项主线合入成果，以及尚未合入的 UEFI 文件双盘实现与已有验证记录。

## 5. 未完成事项

当前剩余问题主要集中在 #2275 的完整交付。已实现、已运行通过和已合入主线分别处于不同阶段，尚不能将整个 UEFI 启动方案记为双平台交付完成。

- **PR 合入**：#2275 仍未合入主线，raw file 后端、PCI 磁盘启动配置、TPM 探测兼容和双盘用例仍保存在功能分支。
- **VMX 与持续验证**：本地 SVM 双盘用例已通过，但 VMX 双盘运行证据尚待补齐；远端 CI 也未实际执行两种后端的 KVM 用例。
- **启动镜像交付**：最终 `/guest/boot.img` 尚未纳入 tgosimages rootfs 制作与发布流程，测试仍依赖临时副本注入，未验证跨次运行持久化。
- **未分配 MMIO 处理**：当前通过固定 TPM TIS 窗口兼容 OVMF 探测，通用的未分配 MMIO 访问处理尚未完成。
