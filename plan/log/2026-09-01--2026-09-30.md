# 9月技术报告

## 目标与问题

9 月继续推进 [Discussion #1604 实习开发计划](https://github.com/rcore-os/tgoskits/discussions/1604) 中的 x86_64 Guest UEFI 主线。8 月已经完成 OVMF/ACPI 验证基线、共享 virtqueue 加固、x86 通用设备 MMIO 解码和通用 vPCI foundation；本月需要在这些基础上完成 virtio-blk PCI 的可运行数据路径，并逐步将 direct-boot 验证推进到 OVMF 可见、可启动的 PCI 磁盘。

Discussion #1604 对这一阶段的目标是：OVMF 通过 PCI 枚举发现 virtio-blk 设备，读取 ESP，并进入 UEFI Shell 或加载 EFI 应用。进入 9 月时，主线仍存在以下问题：

1. 通用 vPCI 已能完成 PCI function、BDF、BAR 和 Linux `lspci` 枚举，但 virtio-blk PCI 的 transport、队列、DMA、设备配置和中断路径还需要完成整合与端到端验证。
2. Linux guest 的 PCI block device 验证尚未形成完整证据链，仍需证明 virtio-pci/virtio-blk driver probe、块请求处理、数据一致性、flush 以及设备中断完成路径确实可用。
3. 当前 E2E 运行在 `APIC: Switch to symmetric I/O mode setup` 和 FPU xstate 初始化阶段存在较长停顿，必须先区分 guest 正常初始化、Axvisor 设备路径阻塞和测试超时，避免用延长 timeout 代替问题定位。
4. virtio-blk PCI 的产品边界仍需在通用 vPCI 和共享 block core 的基础上收敛，避免复制 MMIO 专用实现；只读数据盘、ramdisk 同步读写/flush、INTx 以及后续 MSI/MSI-X 的范围需要分别验证和推进。

因此，9 月的成功标准分为两层：第一层是 Linux guest 能够通过标准 PCI 路径发现并使用 virtio-blk 设备；第二层是复用同一设备和资源规划，让 OVMF 通过 `VirtioBlkDxe` 发现磁盘、读取 ESP 并进入 Shell 或加载 EFI 应用。只有第二层完成后，才能声明 x86_64 Guest UEFI 的 PCI 启动盘链路成立。

## 计划安排

### 第一阶段：完成 virtio-blk PCI 基础数据路径

- [ ] 基于 #2197 的通用 vPCI foundation 接入 modern virtio-blk PCI，复用已有的 transport-neutral block core 和共享 virtqueue，不新增第二套设备模型。
- [ ] 完成 PCI capability、common config、notify、device config、BAR、DMA 和中断状态之间的边界与资源绑定，确保配置空间、firmware 描述和 runtime route 均来自同一 `ResolvedDeviceGraph`。
- [ ] 明确 block backend 的产品契约：初期优先完成确定性的 ramdisk/镜像后端，支持 guest 所需的同步 read、write、flush 语义；只读数据盘能力单独保留可验证的只读约束。
- [ ] 补齐 device reset、queue ready、descriptor 校验、guest memory fault 和错误恢复路径，确保不可信 guest 不能通过畸形 virtqueue 布局越界访问或污染宿主状态。

### 第二阶段：Linux guest 端到端验证

- [ ] 定位并解决 APIC 对称 I/O 初始化和 FPU xstate 初始化阶段的长时间卡点，记录可复现的 guest 日志、超时边界和责任层，不通过放宽成功条件处理。
- [ ] 在 VMX/SVM 共用同一 guest 配置、磁盘镜像和成功断言的前提下，验证 Linux `lspci` 识别 virtio-blk function、分配 BAR 并完成 virtio-pci/virtio-blk probe。
- [ ] 验证 guest 对块设备的实际 read、write、flush 和数据一致性；若使用只读后端，同时验证只读属性、写请求失败和镜像内容不被修改。
- [ ] 验证 virtqueue completion、INTx 触发与清除、guest memory DMA 边界和 reset 后重新初始化，并由 guest 内部 marker 报告结果。

### 第三阶段：OVMF PCI 启动盘路径

- [ ] 将已通过 Linux direct-boot 验证的 virtio-blk PCI 设备接入 OVMF guest 配置，确保 OVMF 看到的 PCI、BAR、DMA 和 IRQ 资源与 runtime 使用的 resolved plan 一致。
- [ ] 验证 `VirtioBlkDxe` 能够枚举该设备并读取 ESP，进一步进入 UEFI Shell 或加载 EFI 应用；成功证据必须来自 guest UEFI/EFI 应用，而不是外层 QEMU 或 Axvisor 启动日志。
- [ ] 在单 vCPU 路径稳定后，整理 VMX/SVM 重复运行记录，评估将 PCI block 与 UEFI 用例纳入持续 CI 的条件；MSI/MSI-X 等扩展能力不阻塞最小启动盘闭环，另行安排实现与验证。
