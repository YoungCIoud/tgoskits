| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| **PCI-disk 路径没有通过 fw_cfg 发布 ACPI**                 | `boots_from_pci_disk()` 路径使用了空的 `FwCfgAcpiBlobs::default()`，虽然低端 direct ACPI image 存在，但 OVMF 实际通过 `fw_cfg` 获取 ACPI，导致 Linux `AE_NOT_FOUND`                                      | PCI-disk 和其他启动方式统一调用 `build_fw_cfg_blobs()`                                                         | **确定的产品 bug**。修复前 fail-first 测试失败，修复后通过。                                                                 |                                      |
| **VirtIO `SIZE_MAX/SEG_MAX` 在 feature 未协商时仍被强制执行** | block request core 根据 config 限制请求，却没有考虑 guest 是否真的协商了对应 feature                                                                                                                 | 将完整 negotiated features 从 PCI/MMIO transport 传到 block core，只在 feature 已协商时应用限制                      | **确定的 VirtIO 协议 bug**，但文档很谨慎：不能证明它就是某次 UEFI 超时的唯一 root cause。                                            |                                      |
| **AMD SVM guest 访问 `0xfed803c0` 导致 NPF**           | AMD Linux 在 late init 中读取 FCH reset-status 固定寄存器，而 AxVisor 没有这个平台兼容设备                                                                                                           | 增加 absent AMD FCH reset-status MMIO compatibility window，返回 open-bus 值而非访问宿主                        | **确定的 SVM 专属兼容问题**。它解释 AMD/SVM 与 Intel/VMX 的差异，不属于 VirtIO。                                               |                                      |
| **第二次 VirtIO level-triggered INTx 永远无法重新注入**       | `guest_type=virtualized` 时 `inject_pending_ioapic_irq_after_eoi()` 因 `uses_passthrough_address_space()` 提前返回，导致 guest-visible vIOAPIC 不执行 `end_of_interrupt()`，`REMOTE_IRR` 不清除 | guest-visible IOAPIC EOI 对 virtualized/passthrough 都处理，把 host IRQ forwarding 的 passthrough 特有逻辑单独保留 | **这次排查里最漂亮、最明确的核心 root cause 之一。** 日志行为与源码状态机一一对应，fail-first 测试也闭合。                                      |                                      |
| **SVM 初次外部中断被 APIC accept 两次**                     | SVM 在 `prepare_external_interrupt_injection()` 已 accept 一次，`complete_event_injection()` 又无条件 accept 一次                                                                          | completion 只有 `reinjected` 事件才补 accept                                                              | **真实后端 correctness bug**。修复前 acceptance:completion 稳定 2:1，单测修复前红、修复后绿；但修完后 guest 仍可能超时，所以不是最终唯一 blocker。 |                                      |
| **fixed external interrupt 没有正确受 APIC PPR 优先级约束**  | ISR 中已有同优先级向量时，VMX/SVM 仍可能继续提交新的 fixed interrupt                                                                                                                                | 增加 `can_accept_interrupt()`，注入前同时检查 CPU interruptibility 与 APIC PPR                                 | **真实中断模型缺陷**，不是单独的最终 root cause。                                                                         |                                      |
| **PPR 阻塞与 interrupt-window 条件混在一起**                | PPR 不允许当前 vector 时也开启 interrupt-window，可能导致“window exit → 仍 PPR blocked → 再开 window”的 host/guest 空转                                                                             | 分离 `cpu_interrupt_allowed` 和 `apic_priority_allowed`；只有 IF/shadow/GIF 不满足才请求 interrupt-window       | **真实控制流 bug**，属于上一项修复后的二次收敛。                                                                             |                                      |
| **传统 PIC 中断被错误压成普通 fixed APIC interrupt**          | PIC 和 IOAPIC 最终都只剩 `{vector, trigger}`，来源丢失，PIC 事件因此错误经过 fixed-vector PPR                                                                                                       | 增加 `LegacyPic`/`legacy_pic` 来源语义，传统 PIC 绕过 fixed-vector PPR，但仍保留 IF/interruptibility 检查             | **真实架构语义问题**。A/B 已证明 PIC 被错误 PPR gate 是 bug，但绕过它后仍未立即恢复启动，所以仍不是唯一 blocker。                               |                                      |
| **PendingEvent 只按 vector 去重，fixed/PIC 来源互相污染**     | 同 vector 的 fixed 与 legacy PIC 事件会合并，并通过 `legacy_pic                                                                                                                             | = ...` 把已有 fixed 事件错误标成 PIC                                                                         | 去重键改为 `vector + legacy_pic`，并允许 PPR-blocked fixed 事件之后的 legacy PIC 被选择                                   | **真实队列语义 bug**，主要影响中断 A/B 的真实性和实际仲裁。 |
| **自动测试命令注入得太早 / shell_prefix 不可靠**                 | 最初用 `~ #`，SVM 根本没有统一 prompt；后来用 `AXVISOR_GUEST_ASSERTION_CASE_UNKNOWN`，但它又发生在 `exec /bin/busybox sh -i` 之前，matcher 100 ms 后就可能把命令写进去                                            | 最终把 `shell_prefix` 移到真正 post-shell 的 `sh: can't access tty; job control turned off`                 | **直接关系到最后测试 PASS 的测试框架 bug。**                                                                            |                                      |
| **运行期诊断错误使用 emergency UART，直接把被测串口抢死**             | runtime console 已接管后，诊断仍调用 `emergency_console::write_fmt()`，触发 `UartRegisterGate` terminal emergency ownership，禁用普通 UART interrupt/worker                                       | runtime 诊断改用安全 diagnostic sink；之后又发现 AxVM 包装层仍走 emergency，再统一改掉并删除危险 wrapper                        | **非常明确的“诊断把系统自己搞坏”问题**。能完整解释 worker 不 dequeue、TX 不前进、queue 64 KiB 饱和。                                    |                                      |
| **ordered guest-output 缺少对 shell consumer 的直接唤醒**  | `OrderedOutput::write()` 只通知 fixed serial worker，shell task 却睡在另一个 `console_progress` WaitQueue；生产者和真正消费者之间缺一跳                                                                  | 非硬中断上下文发布 output 后直接通知 `console_progress`；硬 IRQ 仍走 worker fan-out                                   | **真实 output handoff 缺陷**，有确定性回归断言，但当时不能单独证明是最终 timeout 的唯一原因。                                            |                                      |
| **ordered-output 写失败被吞掉**                          | `OrderedOutput::write()` 满时返回 Err，但 `queue_guest_output()` 无条件返回 `true`，上层误以为发布成功，不走已有 replay fallback                                                                          | 正确传播 publish 结果，失败时触发现有 fallback                                                                    | **真实 output path bug**。                                                                                  |                                      |
